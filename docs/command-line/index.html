Command line

Every command, the body syntax, output options, exit codes and idempotency.

Read, search, create and update STLabs tickets from your terminal or a script. Every command comes from the published API contract.

Access

Access to the STLabs API is not open yet. This release cannot sign in or call the API. To request access, email support@stlabs.com. A refused sign-in or call prints two lines and exits with code 10.

Get started

login signs you in and org set picks the organization every call acts on. status shows the host, whether you are signed in, and which organization is set. logout removes the stored token. See the two sections below for each.

Sign in

login stores the token in the OS keychain. On Linux that is the Secret Service when one is available; on a headless machine set STLABS_TOKEN instead. It reads the token from stdin and refuses one given as an argument, which would end up in your shell history:

STLABS_TOKEN in the environment takes precedence over the keychain; use it in CI and scripts. With neither, a command stops with stlabs: not signed in and sends nothing.

On macOS the keychain ties an entry to the program that wrote it. After reinstalling stlabs, the next command can show a system dialog and wait with no output. Click Always Allow, or set STLABS_TOKEN.

While access is closed, nothing is written to the keychain and nothing is sent.

Organization

Every call names the organization it acts on:

The slug is not a secret, so it is stored in its own file (~/.config/stlabs/config.json by default), not the keychain. STLABS_ORGANIZATION in the environment takes precedence; use it in CI and scripts. With neither set, a command stops with stlabs: no organization set and sends nothing.

A file, read, edit, comment, resolve loop. dana@northwind.example and the northwind organization are sample data, not a real organization. Use a person in yours:

The first and last commands file the same ticket with the same key. The second returns the first ticket instead of filing another.

Three rules

  • Every command that changes something is sent with an idempotency key. stlabs generates a new one each run, so running a command twice makes two changes. To make a retry safe, choose the key yourself with --idempotency-key <key>. The same key with the same body returns the original response instead of a second ticket. It has the same id and the same status, and the header Idempotent-Replayed is "true". The same key with a different body is refused with IDEMPOTENCY_KEY_MISMATCH. When a change fails in a way that is safe to retry, stlabs prints the command to retry it with, key included, unless the command ran with --query or --output (the hint names the key alone then).
  • A body is one argument of field: value pairs, separated by commas. Put the whole body in single quotes. Put a value in double quotes if it contains a comma, looks like a number, is true, false or null, or starts with [ or {. Unquoted, those are sent as something other than text. For example 'title: "Filed, then edited"', 'title: "123"' or 'title: "true"'. A word after the body is refused rather than added to it.
  • A failed call still prints to the same stream a successful one would, and exits non-zero. stlabs prints the response the same way on success or failure. --query and --output apply to a problem body as they apply to a real one, so a selected field prints null on a 404, not nothing. Check the exit code, as in ID=$(stlabs ...) || exit, not whether output came back empty.

Output and exit codes

A command prints the response body as JSON. On a terminal, a command that lists records prints a table of its main columns instead; piped or redirected output is JSON unless --output says otherwise, printed on one line with no trailing newline. --output picks the format: json, yaml, table or lines. A command takes only the options its --help lists.

Shape the output

--query selects part of the response with a JMESPath expression, starting from the whole response (status, headers and body): --query body.id prints the id alone, which is how the examples above capture a new ticket's id into a variable.

A command that reads is retried twice on a 429 or 5xx response, waiting as long as Retry-After asks. Each retry prints warning: retry 1/2 in <wait> on stderr. A command that changes something is never retried automatically. A 5xx or a network failure leaves the server unsure whether the change landed. stlabs then names the read that shows it (for a comment, stlabs tickets comments list <ticket>) and tells you to check with it before running the change again. A same-key retry is safe only on a 429 (RATE_LIMITED) or IDEMPOTENCY_IN_FLIGHT: the first request was refused before it started, or is still running. There stlabs prints the command to retry with, key included.

exitmeaning
0success
1not signed in, no organization set, a body that does not parse, or a network error on a host you set with STLABS_BASE_URL
2a usage error: an unknown command or option, or missing or extra arguments
3the API answered with a redirect (a 3xx response)
4the API refused the request (a 4xx response)
5the API failed (a 5xx response)
10access to the STLabs API is not open yet

A refused token prints stlabs: the API refused the token (expired or invalid) on stderr, before the response itself. Run stlabs login again to sign in with a new token. A problem body carries a stable code to branch on, a detail for people, and retryable.

Versions

Versions are handled for you: every command pins the API version it was built for (STLabs-Version: 2026-09-14) and names your organization; every change carries an idempotency key.
