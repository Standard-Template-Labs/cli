Command line

Sign in, do everyday tasks, script with output and exit codes, and fix common problems.

Work with your STLabs organization from your terminal or a script.

Quick start

Install stlabs first. The Install page has the steps, and stlabs --version shows what you have. Your organization's slug is the short name after /org/ in your STLabs web address. It is often different from the display name, so copy it from the address. Then sign in, choose your organization, and list the open tickets you requested:

stlabs login opens your browser. Sign in with your usual account. On a Linux server with no keyring running, stlabs login --device fails with the keychain is not available, so follow Sign in on a Linux server instead. On any other machine with no browser, use stlabs login --device. Sign in covers every way to sign in.

stlabs org set does not check the slug, so a wrong one fails on the first command that calls the API. Troubleshooting shows what that looks like.

The last command prints a table of your open tickets, newest first:

To let an AI agent use stlabs, run stlabs setup. See Agents.

Sign in and choose an organization

Sign in

To sign in withRunUse it for
A browserstlabs loginYour own computer.
A codestlabs login --deviceA machine with no browser. Open the address it prints on another device and type the code.
A tokenstlabs login --with-tokenA script that already has a token.

Signing in saves a session in your keychain. On Linux, the keychain is a keyring that the Secret Service provides, and a server often has none: see Sign in on a Linux server. Before any command that calls the API, stlabs refreshes a browser or device session. You sign in again only when that session expires or is revoked. A token you paste with --with-token is stored as it is and is not refreshed, so replace it when it expires.

--with-token reads the token from standard input. It refuses a token given as an argument, because the argument would end up in your shell history:

In CI and scripts, set STLABS_TOKEN instead. It takes precedence over the saved session. Get a token with stlabs auth token on a computer where you are signed in. It expires, so it suits short jobs.

To check or end a session, use these commands:

CommandWhat it does
stlabs statusShows the host, who is signed in and how (a browser, a device code, a pasted token or STLABS_TOKEN), the organization, and whether your agent may write without asking (agent writes, see Agents). Exits 1 when you are not signed in.
stlabs whoamiPrints your email on one line, or nothing when the token does not belong to a person.
stlabs auth tokenPrints the current access token for a script. It refreshes a browser session that is about to expire first. When the token comes from STLABS_TOKEN or --with-token, it prints that token as it is.

Choose an organization

Every call acts on one organization. stlabs org set <slug> saves it and stlabs org status shows it. STLABS_ORGANIZATION takes precedence over the saved slug, so CI and scripts can set it without writing a file.

The slug is not a secret. stlabs keeps it in a settings file, ~/.config/stlabs/config.json by default, and not in the keychain. Environment variables lists how to use a different path.

Everyday tasks

Work through a ticket

These commands file a ticket, read it, edit it, comment, resolve it and list tickets. The last command files the first ticket again with the same idempotency key, which Retries and idempotency explains. Replace dana@northwind.example with the email of someone in your organization, or to file for yourself, use --requester me in place of --requester-email. A Linux machine without uuidgen can make a key with cat /proc/sys/kernel/random/uuid. The northwind organization is sample data, not a real organization.

The last command returns the first ticket's original response and files nothing new. Retries and idempotency explains why.

To open a ticket in your web browser, run stlabs tickets get <id> --web. It prints the address instead when there is no browser to open.

Find tickets

stlabs tickets list takes a text search and filters. They combine, and each one narrows the list. The newest tickets come first. A search that matches nothing succeeds with an empty list.

--created-after, --created-beforeA date such as 2026-10-01, which means midnight UTC, or a full time such as 2026-10-01T00:00:00Z. --created-after includes the time and --created-before does not. --created-before 2026-10-31 leaves out the 31st.

Scripting

Output formats

On a terminal, stlabs shows what a person needs:

  • A command that lists records prints a table. It shows the columns you need to pick a record and shortens the longest column, such as the title, to fit the window.
  • A command with a readable view, such as stlabs tickets get, shows one record.
  • A command that changes something prints one line saying what changed, then the command to run next.
  • Any other command prints JSON.

The readable view and the success line appear only when the call succeeded. In a narrow window, a long text column moves to a second line. The row starts with ● and its text follows └. Ticket ids in lists, in the ticket view and in the line after you file or change a ticket are links to the ticket, in terminals that can show links.

When the output is piped or redirected, stlabs prints JSON on one line that ends with a newline. A --query result that is JSON is indented. --output picks another format on a terminal or in a pipe:

--outputPrints
jsonThe response as JSON.
yamlThe response as YAML.
tableA list of objects as a table, or one record as a key-value table with nested keys joined by dots. The table is as wide as $COLUMNS, or the window, or 80 columns when piped with no $COLUMNS. Piped, it has no color.
linesOne value per line. It needs --query.

With no --output, a --query result that is text prints as text and anything else as JSON. An object that a query builds keeps its fields in the order the query lists them, in JSON, YAML and table columns. The fields of an object the API sent come back in alphabetical order.

On a terminal, control characters in text printed with --query or --output show as escapes such as \x1b. Tabs and line breaks stay as they are. Piped, the text is exactly as the API sent it.

Pick values with --query

--query selects part of the response with a JMESPath expression. The expression starts from the whole response, which has status, headers and body. For example, --query body.id prints the id alone. The examples above use it to capture a new ticket's id.

To getWrite
One field--query body.id
A field inside a field--query body.requester.display_name
One item of a list--query 'body.items[0]', or 'body.items[-1]' for the last
The first two items--query 'body.items[0:2]' (the end is not included)
One field of every item--query 'body.items[].id'
The items that match--query "body.items[?state=='open']"
Some fields of every item--query 'body.items[].{id: id, state: state}'
How many items--query 'length(body.items)'
A header, or the status--query 'headers."Idempotent-Replayed"', --query status

Inside the query:

  • Write text in a condition in single quotes, as in state=='open'.
  • Double quotes name a field. That is how you write a header with a dash in its name.
  • Write a number in a condition in backticks, as in [?n > `2`].
  • Compare with ==, !=, <, <=, > and >=. Join conditions with &&, || and !.
  • Functions such as length, sort_by, contains and starts_with are available.

In your shell, put the whole query in single quotes. When the query itself holds single quotes, put it in double quotes instead, as in "body.items[?state=='open']". Inside double quotes, the shell runs anything in backticks as a command, so put a backslash before each backtick of a number, as in "body.items[?state=='open' && n > \`2\`]".

stlabs checks the syntax of the query, the functions it calls and where it starts before it sends anything. A query that cannot run exits with 2 and nothing is sent, so a typo never makes a change and then prints null.

If the query does not fit the response, such as length of a number, stlabs prints nothing and exits 1. That is found only after the response arrives. When the command made a change, the change is still saved: stlabs says Your change was saved and names the command that shows it. A well-formed query for a field the response lacks prints null.

Long lists

A list that takes --limit returns a set number of records by default, 25 for stlabs tickets list. Run stlabs <command> --help to see whether a list takes --limit and --all. When more records exist, stlabs prints a note on stderr after the table or the JSON, whatever you set for --query or --output. Stdout keeps only what you asked for. The note looks like this:

A second line, not shown here, is the command that carries on from the last record: your command again, with its own --cursor.

To getUse
More than the default--limit 250, which fetches 250 records a request at a time and prints them as one table or one JSON response.
Every record, up to 1,000--all
More than 1,000 records--all --max 5000
The next recordsThe printed command, or --cursor with the next_cursor from the JSON. Keep the same search and filters.

A run fetches records a request at a time and stops after 100 requests. A request holds up to 100 records for stlabs tickets list, so a run reaches 10,000 records. Other lists have their own request size, which stlabs <command> --help names. stlabs refuses a larger --limit or --max before it sends anything. It says what the ceiling is.

The JSON is {"items": [...], "next_cursor": ...}, whether it holds one page or many. next_cursor follows the last record printed and is null at the end of the list. With --query, keep the cursor in the result: --query '{ids: body.items[].id, next: body.next_cursor}' returns next as null at the end.

A run that ends with records left still exits 0, because it returned all it was asked or allowed to. That includes a run that stopped at the page cap, where stderr says Stopped after 100 pages. Check next_cursor to know whether more remain.

With --all, stlabs applies a --query or --output once, to the merged response. So --all --query 'body.items[].id' prints the ids from every page. A query over several pages reads the status and headers of the last page. If a page fails partway, stlabs exits with that failure's code, says how many records it fetched, and prints no combined response.

Exit codes

stlabs help exit-codes prints the same table.

exitmeaning
0success
1not signed in, no organization set, a response that could not be read (empty, or not from the API), or a network error
2a usage error: an unknown command or option, a query or body that cannot be used
3the API answered with a redirect (a 3xx response)
4the API refused the request (a 4xx response); retry only when the response says it is retryable, after any wait it names, and retry a change with the same key
5the API failed (a 5xx response); a change may or may not have been saved
11the API no longer serves what this stlabs asks for: an API version it dropped (install the latest stlabs) or a command it removed (stlabs --help shows what replaces it)

A 404, such as an unknown ticket, is exit 4. Exit 11 means the API changed, not that you made a mistake: see Troubleshooting.

Retries and idempotency

What stlabs retries. A command that gets or lists records is retried twice on a 429 or 5xx response or a network error. It is not retried when the error says retryable is false.

  • It waits as long as Retry-After asks, up to 12 seconds, plus up to a quarter more so that callers refused together do not come back together. The wait is never more than 15 seconds.
  • When Retry-After asks for more than 12 seconds, stlabs does not wait. It exits with the response's own code (4 for a 429) and says how long to wait.
  • Each retry prints warning: retry 1/2 in <wait> on stderr.

A command that changes something is never retried automatically, and neither are stlabs people availability search, stlabs queues search, stlabs tickets counts get and stlabs tickets translations list, which read with a POST.

After a failure. A 5xx response or a network failure often leaves it unclear whether a change landed. stlabs names the read that shows it, such as stlabs tickets comments list <ticket> for a comment. It tells you to check before you run the change again. When the host cannot be reached at all, because the host refused the call or its name was not found, nothing was sent, and stlabs says so.

Idempotency keys. An idempotency key is a string that tells the API two requests are the same change. Every command that changes something is sent with one. stlabs makes a new key on each run, so running a command twice makes two changes. To make a retry safe, choose the key yourself with --idempotency-key <key>.

For a day after a key is first used, the same key never makes a second change:

You sendYou get
The same key and the same bodyThe original response, with the same id and status and the header Idempotent-Replayed set to true.
The same key while the first attempt is unfinished or its outcome is unknownA refusal that says to wait or to check first.
The same key and a different bodyA refusal with the code IDEMPOTENCY_KEY_MISMATCH.

When a change fails in a way that is safe to retry, stlabs prints the command to retry with, key included, on a line of its own. A refusal because too many keys are in use prints no command. The same key does not help until older keys expire.

Errors you can branch on

A failed call exits non-zero, and never prints an error where a value should be. Where the error goes depends on how you ran the command:

How you ran itWhat you get
Piped, or with --output, and no --queryThe error body on stdout. Piped, it is exactly as the API sent it. With --output json or yaml it has the same fields in that format. With --output table it is a key-value table.
On a terminal, with no --output or --queryA line on stderr that says what went wrong and what to do, then request id: <id>. Quote that id when you ask for help.
With --queryNothing on stdout, and the error body on stderr. This keeps an error from being read as the value you asked for.

The exit code stays the same in every case. Check it, as in ID=$(stlabs ...) || exit, and not whether any output came back.

The error body has these fields:

FieldWhat it holds
codeWhat went wrong, such as NOT_FOUND. Stable. Branch on it.
reasonA finer cause, where one applies. Stable.
retryableWhether a retry can work. Stable.
next_stepsWhat to do. Each step has a kind, such as allowed_values. Stable.
detail, hintText for people. It can change in any release.

Agents

stlabs setup gets you and your AI agent ready in one command. On a terminal it:

  1. Offers to sign you in. --device signs in with a code instead of the browser.
  2. Picks your organization. After a browser sign-in it uses the one you are signed into on the web. It asks only when that does not settle it.
  3. Installs the agent skill.
  4. Asks whether your agent may file tickets and add comments without asking you first.
  5. Ends by telling you what to ask your agent first, or the command still left to run.

A step that is already done is skipped, so you can run stlabs setup again at any time. With -y, or with no terminal, it asks nothing and prints one key: value line for each step, with next: for what is left. Add --output json to print the result as JSON.

stlabs setup --status prints the same lines and changes nothing. It exits 0 when the skill is current in every folder, and 1 otherwise. A missing sign-in or organization does not change the exit code. A relative CLAUDE_CONFIG_DIR is refused with exit code 2.

The agent skill

The skill is a set of instruction files that tells Claude Code and other agents how to use stlabs. Installing it sends nothing and never edits an agent's settings. It goes into these folders:

  • ~/.claude/skills/stlabs-cli
  • ~/.agents/skills/stlabs-cli

When CLAUDE_CONFIG_DIR is set to an absolute path, the first folder is $CLAUDE_CONFIG_DIR/skills/stlabs-cli. If setup creates ~/.claude/skills for the first time, a Claude Code session that is already running needs /reload-skills.

--status reports one of four states for each folder:

StateWhat setup does
CurrentNothing.
OutdatedReplaces it.
Changed since it was installedOn a terminal, asks before it replaces your edited copy. -y replaces it without asking. With no terminal and no -y, it leaves the copy as it is.
Not installedInstalls it.

If you keep an edited copy, setup skips the question about tickets and comments.

What your agent may do without asking

setup asks whether your agent may file tickets and add comments without asking you first:

AnswerWhat the agent does
confirm (the default)Asks before it files a ticket or adds a comment.
routineFiles tickets and comments on its own.

Whatever you choose, the skill tells the agent to ask before it resolves, updates or deletes anything, or makes a bulk change. The skill only asks the agent to stop. Your agent tool's own permission prompts are the check that holds.

Run setup again and it shows your answer and asks whether to change it. To set it without a question, use --agent-writes confirm or --agent-writes routine. With -y, setup keeps the setting you have, or confirm if there is none. stlabs status and stlabs setup --status show it as agent writes.

What your agent can read

stlabs agent schema prints the commands of the stlabs installed on this machine. An agent can read them even when its skill is older than stlabs. It needs no sign-in and sends nothing. It prints JSON when piped or with --output json, and text on a terminal.

CommandPrints
stlabs agent schema tickets createOne command: its flags, fields, examples, and when it is safe to run again.
stlabs agent schema ticketsA group: each command with its field names.
stlabs agent schema --search <word>The commands whose names or summaries match the word.

Run without a name, it lists every command of stlabs. For commands that stlabs answers itself, such as login and setup, it prints their usage.

Flags and bodies

Flags

A command takes only the options its --help lists. stlabs <command> --help lists every flag, the keys of each object and the field each flag sets.

Every field that takes a value has a flag, named after the field with _ written as -: --title, --priority, --queue, --assignee and the rest.

ForWrite
A field that offers alternativesA flag named after the alternative you pick. stlabs tickets transition takes --state.
A list you can add to and remove fromA flag for each verb: --add-follower and --remove-follower.
The settings of an objectOne flag named for the object, with a key for each setting: --awaiting-reply close-hours=48 --awaiting-reply then=cancel. The value is everything after the first =, as typed.
A field that holds several valuesThe flag once for each value. Ids may also be separated by commas. Free text never is.
A true or false fieldThe flag alone for true, and --flag=false for false.
A field that can be left empty--clear <field> unsets it. Repeat it for more fields.

stlabs sends the value of a flag exactly as given. Commas, colons, quotes, @me and text that looks like a number need no quoting except your shell's. A body follows different quoting rules: see Bodies.

Text from a file or the editor

A comment, a description, a reason or a note takes --body, --description, --reason or --note. Add -file to the name to read the text from a file, or from standard input with -. The text is sent exactly as given, with its commas, quotes, brackets and line breaks.

Keep text in one shell argument, as in --body 'Thanks, that fixed it'. To read a comment from a pipe, run stlabs tickets comments create "$ID" --body-file -.

On a terminal, a comment with no text opens the editor named by VISUAL or EDITOR. With neither set, or with no terminal, the command stops with exit code 2 and says how to give the text.

Bodies

A body is one argument of field: value pairs separated by commas. It goes after the other arguments, as in stlabs tickets update <ticket> 'title: "Filed, then edited"'. It is the only way to give a field that holds an object, such as business_hours.

  • Put the whole body in single quotes.
  • Put a value in double quotes if it contains a comma, starts with @, looks like a number, is true, false or null, or starts with [ or {. Unquoted, those are sent as something other than text.
  • Give a field by its flag or in the body, not both.
  • A word after the body is refused rather than added to it.
You wantWrite
A title with a comma'title: "Filed, then edited"'
A title that is a number'title: "123"'
A title that is the word true'title: "true"'
An assignee of @me, which starts with @'assignee: "@me"'

When the API has retired a command or an API version, a terminal shows a short line. Piped, or with --output, the whole error body is printed, and the exit code is the signal.

A retiring command prints its warning once per run, on stderr. A command the API is retiring without a date prints the same line, saying it is going away. A command the API has already retired does not warn. It fails with exit code 11. The warning is a notice, so it is not shown when output is piped or --output is given. STLABS_NO_NOTICES=1 hides it.

Sign in on a Linux server

On Linux, stlabs keeps your session in a keyring that the Secret Service provides. stlabs login with no terminal stops with no token given. stlabs login --device fails with the keychain is not available while no keyring is running. You have two ways to sign in.

Copy a token from your own computer. On a computer with a browser, run stlabs login, then run stlabs auth token. On the server, set its output as STLABS_TOKEN and set STLABS_ORGANIZATION. The token expires, so this suits a short job.

Run a keyring on the server. On Debian or Ubuntu, install the packages, start a shell under dbus-run-session, and unlock a keyring with a passphrase you choose. The passphrase is typed at a prompt, so it stays out of your shell history:

Run your stlabs commands in that shell. The keyring lives in ~/.local/share/keyrings, locked with that passphrase, and is open only while the shell runs. The next time you log in to the server, start the shell the same way (dbus-run-session -- bash, then the read and eval lines) with the same passphrase. You stay signed in.

To run a command without a shell that stays open, such as in a script, set KEYRING_PASSPHRASE to the passphrase and put the unlock in front of the command. It is an ordinary environment variable: set it in the shell or pass it to the job, and do not write it into the script. The first time, run stlabs login --device this way. Commands

stlabs has these groups of commands:

GroupWhat it covers
ticketsCreate, find, update and comment on tickets
approvalsReview and answer approvals waiting on you

To see the commands:

  • stlabs --help lists the groups.
  • stlabs help commands lists the commands of every group on one page. It works offline and when you are signed out.
  • stlabs tickets --help lists the commands in a group.
  • stlabs tickets create --help shows the arguments in order, the body fields and an example.

The commands in these groups call the STLabs API. The rest are built into stlabs: login, logout, status, whoami, org, setup, auth token, agent schema and help. They manage your session, your settings and the agent skill.
